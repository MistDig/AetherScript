# SQLite variable baseline

`SQLiteVariables` is a blocking Java service, separate from the existing JSON service. It has no Bukkit dependencies and no script syntax, tick scheduling, or plugin activation. The host must select its storage explicitly and dispatch every constructor/read/commit/close call onto a bounded owner-managed worker. There is no automatic JSON migration.

The service reuses `PersistentVariables.Key`, `Value`, `Entry`, and `Mutation`. Feature namespace and optional canonical player UUID identify each typed text/integer/boolean key. Revision zero means absent. A commit contains 1–128 distinct mutations and compares all expected revisions in one `BEGIN IMMEDIATE` transaction; a stale revision rejects the whole batch. At most 4096 keys are allowed. Reads return a fresh immutable transaction snapshot, including changes committed through another connection. SQLite's busy timeout is 5 seconds; a lock timeout is an I/O failure, distinct from a stale revision conflict. Retrying requires host policy.

Schema version 1 uses `PRAGMA user_version`; only an empty unversioned database is initialized. Unknown versions and invalid persisted types/UUIDs/revisions fail closed. There is no destructive schema upgrade. Use an owner backup before any future explicit migration. SQL identifiers and commands are fixed; all persisted values use prepared statement parameters.

The pinned provider is [Xerial SQLite JDBC 3.54.1.0](https://github.com/xerial/sqlite-jdbc/releases/tag/3.54.1.0), from Maven Central, carrying SQLite 3.54.1 and native platform libraries. Native extraction uses the provider's configured temporary directory; deployment must allow native library loading. The service selects rollback DELETE journaling and synchronous FULL. The database is capped at 6144 pages (24 MiB with the new database's default 4096-byte pages); transactions can temporarily require an additional rollback journal approximately the database size. This is a logical storage bound, not a disk reservation or guarantee of OS power-loss behavior. Native caches, filesystem allocation overhead, and temporary provider extraction are additional. No vacuum, delete, backup, export, or import API is supplied in this slice.

Use an owner-controlled local directory and filesystem with working SQLite file locks. The service rejects symlink directory traversal and non-regular existing database/sidecar files. It rejects hard-linked existing files on providers exposing Unix link counts. Java's portable Windows file attributes do not expose hard-link counts; owners must prevent untrusted file creation and replacement through directory ACLs. Checks before open cannot protect against hostile concurrent filesystem replacement. Network filesystems and attacker-writable directories are unsupported. Multiple service connections in that trusted directory are supported; SQLite manages their database locks.

Tests use actual SQLite databases for restart persistence, typed namespace/player separation, competing-connection CAS, atomic invalid-batch rejection, key limits, unknown schema, and strict persisted codec rejection. These are unit/integration tests of the Java service; they are not real-server or script integration evidence.
